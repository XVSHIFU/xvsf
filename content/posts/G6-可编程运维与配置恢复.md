从 host31 通过 RESTCONF 将全部实际 VTY 范围的 input 从 none 改为 all，并回读复核。

VTY 是设备的远程终端线路，`transport input none` 关闭通过这些线路接入的协议。RESTCONF 使用 HTTPS 服务，与 VTY 接入通道不同；在 HTTPS、认证及 RESTCONF 已配置的前提下，可通过 API 修改 VTY。

YANG 描述资源结构，URL 定位 VTY 列表。GET 读取实际 first/last 范围，PATCH 只修改列表键对应的 `transport.input`，再次 GET 对照原范围及 `all` 值。`login local` 等其他参数保持原值。

HTTP 200 表示本次读取成功，PATCH 的 HTTP 204 表示服务端接受且无响应正文；最终配置以回读和 CLI 复核为依据。



课程访问路径为 host31→`https://10.3.11.1/restconf/data/Cisco-IOS-XE-native:native/line/vty`。操作范围为 API 返回的全部可配置 VTY，input 从 none 改为 all，再 GET 回读；控制台仅用于前置基线和结果复核。

### API 脚本与调用方式

[restconf_ops.py](/xvsf/uploads/ccie/ccie-g6/restconf_ops.py) 提供 `vty-plan` 与 `vty-apply`。它读取服务端返回的所有 first/last 范围，生成仅包含列表键和 transport.input 的 PATCH，保留其他 VTY 参数。修改前、PATCH 和回读分别落盘，回读核对范围集合和 all 值。

通用脚本调用格式如下。管理机阶段使用 CSR DHCP 管理地址；host31 阶段使用后文的 Python 2.7 实验脚本和课程地址 `10.3.11.1`。

```text
python restconf_ops.py vty-plan 10.3.11.1 --username admin --out evidence --insecure-lab
python restconf_ops.py vty-apply 10.3.11.1 --username admin --out evidence --insecure-lab
```

密码交互输入，或使用 `CCIE_RESTCONF_PASSWORD` 环境变量。实验自签名证书才显式使用 `--insecure-lab`；默认验证证书。两条实测路径分别记录为管理机访问和 host31 访问。

在设备 Guest Shell 中运行 Python，动态识别非默认 VRF 及地址族并采集路由表。

Guest Shell 是 IOS-XE 提供的 Linux 执行环境，`cli` 模块将 Python 查询交给设备 CLI。脚本每次从设备读取 VRF 清单和地址族，以当前配置决定查询范围。

IPv4 VRF 使用 `show ip route vrf`，IPv6 VRF 使用 `show ipv6 route vrf`，双栈分别查询。RD 是否配置与地址族是否启用是不同字段，脚本保留空 RD 的兼容处理。

### 脚本逻辑与执行方式

[ribdump.py](/xvsf/uploads/ccie/ccie-g6/ribdump.py) 每次读取 `show vrf brief`，识别 IPv4、IPv6 或双栈 VRF，分别调用：

```text
show ip route vrf <name>
show ipv6 route vrf <name>
```

跳过 default/global 和没有 IP 地址族的项，兼容 `<not set>` RD。脚本通过 Guest Shell 的 `cli` 模块执行命令，不预写 VRF 清单，不查询未启用的地址族。

真实 r30 上需先核对 IOx/Guest Shell 支持和已有 VirtualPortGroup。如果需要专用网络，按题目使用 192.168.255.0/24 且不发布进路由协议。脚本放在 Guest Shell 用户家目录，执行：

```text
guestshell run python ribdump.py
```

真实 Guest Shell 已完成脚本运行及动态新增 VRF 验证，环境配置与输出见实机记录；离线测试单独记录解析和错误处理。

### Guest Shell 配置与脚本实测

使用设备自带的 Guest Shell 2.5.1／Python 2.7.5。按题目允许的网段建立 VirtualPortGroup0：设备 192.168.255.1/24、容器 192.168.255.2/24，未配置路由协议发布该网段。

```text
configure terminal
iox
interface VirtualPortGroup0
 ip address 192.168.255.1 255.255.255.0
exit
app-hosting appid guestshell
 app-vnic gateway1 virtualportgroup 0 guest-interface 0
  guest-ipaddress 192.168.255.2 netmask 255.255.255.0
 exit
 app-default-gateway 192.168.255.1 guest-interface 0
end
guestshell enable
```

首次容器虽显示 RUNNING，`guestshell run` 连续报 `access test command failed`。停用再启用未解决；重建这个尚未保存脚本的新容器后，Python 命令可以运行。重建前诊断、重建后 Python 版本。这是容器重建，没有对 EVE 节点执行 Wipe。

脚本第一次调用 `cli()` 又出现 PnP socket 错误。该版本的内置 CLI 通道需要 HTTP 服务创建本地 socket：启用 `ip http server`，等待 `/cisco/nginx_shared/pnp_python.sock` 出现后，脚本取得实际路由输出。管理接口入口过滤 TCP/80，保持该服务供内部调用，外部 RESTCONF 仍使用 HTTPS。配置如下：

```text
configure terminal
ip http server
ip access-list extended G6-MGMT-IN
 deny tcp any any eq 80
 permit ip any any
exit
interface GigabitEthernet1
 ip access-group G6-MGMT-IN in
end
```

HTTP 本地通道与首次成功输出。启用条件参考 [Cisco 16.12 Guest Shell 文档](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/prog/configuration/1612/b_1612_programmability_cg/guest_shell.html)。本次管理机实测 TCP/80 被过滤，HTTPS 配置备份仍成功。

`ribdump.py` 通过临时 HTTP 文件服务复制到 CSR bootflash，再复制进 `/home/guestshell/`；文件服务已停止。设备脚本与本地脚本核对 SHA-256。为兼容 Python 2.7，将 `re.fullmatch()` 改为带首尾锚点的 `re.match()`，VRF 清单仍在每次执行时动态读取。

```text
copy http://192.168.1.19:8089/ribdump.py bootflash:ribdump.py
guestshell run cp /bootflash/ribdump.py /home/guestshell/ribdump.py
guestshell run python ribdump.py
guestshell run sha256sum /home/guestshell/ribdump.py
write memory
```

批量保存 RESTCONF 配置数据，核对 CLI/EVE 阶段备份及独立恢复依赖。

RESTCONF native JSON 保存 YANG 资源数据，CLI 文本保存 IOS 命令，EVE ZIP 保存实验定义及导出的启动配置。三种文件的内容和恢复方式不同。

API 备份依次检查 HTTP 状态、JSON 格式及 native 根资源，再生成带时间戳的文件和 SHA-256。哈希用于核对文件内容，独立恢复还需要匹配平台、导入方式与启动验证。



### RESTCONF 备份方式

同一脚本的 `backup` 动作 GET native 根资源，检查 HTTP、JSON 和 native 根，再保留时间戳文件及 SHA-256 清单。设备失败单独报告并继续其他设备，最终返回失败状态，避免把错误页面当作成功备份。

```text
python restconf_ops.py backup 192.168.1.1 192.168.1.2 --username admin --out backups --insecure-lab
```

课程给出的凭据例子用于理解循环结构，不作为本环境真实凭据。若设备用户名不同，分别调用。按 IP 展示和选择设备时，`{IP: (username, password)}` 字典可直接索引；课程参考答案选 d（元组列表）也能遍历，但题目所述按 IP 选择时 c 更直接，此差异保留说明。

RESTCONF native JSON 与 IOS CLI 文本是不同备份格式，不能直接当配置命令粘贴。回滚应按对应 YANG 资源生成逆向变更、回读核对并验证业务；当前没有执行真实 RESTCONF 恢复。

### 脚本离线验证

测试脚本 共 7 项通过：证据文件名保留完整 IP 与时间戳、单/双栈及空 RD 解析、只查询启用的地址族、全部 VTY 范围、非法 VTY 数据拒绝、HTTP 失败和 YANG 错误响应拒绝。输出见 offline-tests.txt。这些测试使用明确的本地样本，没有伪造真实设备返回。

## 业务诊断、访问安全与恢复资料

business_diagnose.py 一次读取混合网关接口、Track、静态路由、NAT，并从实际分支客户端发起两个 HTTPS 请求。接口和业务均正常输出 PASS；单路故障但业务可用输出 DEGRADED；业务失败输出 FAIL。关闭上联时，报告能明确指出 SD-WAN 或 DMVPN 的本地接口被管理性关闭，保留原始输出供排障。

```powershell
D:\ProgramAll\anaconda3\python.exe tools/G6/business_diagnose.py current
```

最终报告及原始命令输出可直接回看。脚本采用明确规则判断，不代表 DNA Center 已部署，也未做故障定位效率的百分比测量。

订单服务使用 TLS 1.2及以上、自建实验 CA 信任验证、随机访问密码和请求审计。未认证请求返回401，数据库仅提供只读订单查询。设备间保留已有 IPsec、VPN 隔离和路由策略。这些是实验安全控制，不能单凭本实验认定通过等保三级测评。

服务位于 EVE 的 `/opt/ccie-business-lab`，凭据文件和私钥权限受限；笔记不粘贴密码。数据、证书、启动脚本及最新 UNL 保存在私有业务备份，保存清单记录配置导出结果。

EVE 重启并启动相关设备后执行：

```bash
bash /opt/ccie-business-lab/start.sh
```

脚本恢复四个 namespace 与 veth 到实验桥，并启动两个服务。实验桥编号须与本项目保持一致：DC63、云64、总部2、混合分支65。只恢复 UNL 不会恢复 Linux namespace 服务文件，需要同时还原私有 tar.gz。未安装定时任务或额外常驻监控。
