### BGP 与防回灌配置

**本轮节点运行条件核对（2026-10-27）**

检查 r11 的邻居接收计数后，通过 EVE API 核对依赖节点：SP1 的 r3 已运行，但核心 r1/r2 和远端 PE r4/r5/r6 均停止，IaaS 的 r30-IOL-IPv6 也停止。HQ/DC 的 r11/r12、r21/r22、r23/r24、sw201/sw202/sw211/sw212，以及 Global_SP2、Internet_SP 均运行。

因此本轮不是完整 SP1/MPLS VPN 环境运行状态：r11—r3 的本地 BGP 会话可以建立，但停止的核心及远端 PE 会影响远端 VPN 路由与业务。此前邻居接收为0的采样保留为不完整依赖下的结果，不能直接归因于过滤或 BGP 配置，也不能断言全部由停机解释；依赖启动并收敛后需重新核对。互联网出口已验证的结果属于仍在运行的 Internet_SP 路径。

运行状态原始记录见 节点状态清单。

**r11 接口与 BGP 采样（2026-10-27）**

Ethernet0/0 为 `100.3.11.2`，e0/1 为 `10.1.99.1`，e0/2 为 `10.1.13.1`，e0/3 为 `10.1.10.1`，Loopback0 为 `10.1.255.11`，均 up/up。结合接口映射，分别连接 SP1 r3、r12、sw102、sw101。

`show ip route bgp` 未列出 B 路由，仅有代码说明和默认出口提示；当前 IP 路由表没有 BGP 来源条目，默认出口指向 `10.1.13.2`（sw102）。空 B 路由表与空 BGP 表含义不同，本次未据此直接判定运营商功能故障。

只读查询实际设备后确认：r3 已向 r11 的通告清单列出 DC 前缀；r11 IPv4 地址族应用 `neighbor 100.3.11.1 filter-list 20 in`，AS path access list20 为 `deny _65002_`、`permit .*`，拒收包含 DC AS65002 的路径。邻居详细输出同时列出入方向 filter-list 拒绝计数29，以及 AS_PATH loop 拒绝计数；返回的 HQ 路径含本地 AS65001，会触发防环检查。前述0是当前策略接受后的计数，不是会话不通或运营商没有路由。

该入方向过滤用于限制 HQ 经 SP1 接收 DC 路径，符合两站优先使用直连并限制经 SP1 互通的设计方向；完整双向隔离与严格题面约束仍按本篇既有差异记录，未仅凭此项宣布整体达标。本轮未修改策略。

原始输出：r3 前缀及通告检查、r11 实际邻居策略与拒绝统计、AS_PATH 过滤列表20。

**同一 DC 前缀的 OSPF 与 BGP 对照（2026-10-27）**

查询 `10.2.255.211/32`：IP 路由表来源为 OSPF1，区域内路由，距离110、metric31，两个等价下一跳分别为 `10.1.13.2` / Ethernet0/2（sw102）和 `10.1.10.2` / Ethernet0/3（sw101）。这决定本机到该服务地址的实际转发；输出星号不单独作为特定业务流逐跳路径的证明。

BGP 表中同一前缀只有一条候选，显示 `Local`、`from 0.0.0.0`、`weight 32768`、`sourced`、`best`。结合路由表的重分发信息，该条目来自 r11 本地将 OSPF 路由引入 BGP，不是从 SP1 邻居接收。`Origin incomplete` 是重分发路由常见的来源属性，不表示路由报错。

![r11 到同一 DC 地址的 OSPF 转发路由与本地 BGP 条目](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/3e09351c803052eb17b3.png)

`best` 表示 BGP 内部选出的最佳候选，不能直接等同于 IP 路由表采用 BGP。该样本同时存在 OSPF 转发路由和 BGP 发布条目，解释了邻居接收为0、BGP 全表仍有前缀、`show ip route bgp` 却为空可以同时成立。此结论针对当前查询前缀，其他条目来源需逐项核对。


客户边界的 OSPF 与 BGP 双向重分发存在反馈风险：一条路由从 BGP 进入 OSPF，又可能从另一台边界重新进入 BGP。`tag 150` 标记首次引入 OSPF 的路由，TAG 策略在反向引入 BGP 时拒绝这个标记，其余路由允许通过。

`next-hop-self` 将 iBGP 通告的下一跳改为本机，解决对端无法解析外部下一跳的情况。AS_PATH 过滤限制包含指定 AS 的 BGP 路径；路由经过 OSPF 后重新本地产生时，原 AS_PATH 不会自动保留，因此本实验另有前缀保护策略和题面约束差异。

r11—r3、r21—r3、r22—Global_SP2的eBGP已建立，r21/r22 iBGP添加next-hop-self。各CE用同一个TAG策略阻止带150标签的OSPF路由回灌BGP：

```text
route-map TAG deny 10
 match tag 150
route-map TAG permit 20
router ospf 1
 redistribute bgp <本地AS> subnets tag 150
```

OSPF→BGP在原redistribute上附加route-map TAG，保留原match选项。r21/r22对SP入方向：

```text
ip as-path access-list 1 deny _65001_
ip as-path access-list 1 permit .*
router bgp 65002
 neighbor <SP对端> filter-list 1 in
```

本副本的同一OSPF区域同时携带HQ/DC路由，DC本地重分发会失去原AS来源。实际还添加出方向HQ-NO-SP前缀列表，拒绝10.1/16及明细，其余放行，防止HQ前缀从DC重新发布。该保护超出题面仅按 well-known mandatory 属性过滤的限制；参考方案也使用额外前缀列表，本副本将其记为约束差异。对原重分发命令附加参数，也应与“不得修改既有命令”的字面限制区别记录。

正常状态r11到10.2.255.211走OSPF intra-area，经总部交换机；本地重分发BGP路径weight32768优于SP路径。这不证明两条直连断开后没有单向SP路径，所以另外保留中断、路由和业务检查。

### r11 自动选路修复

此处涉及两层选择：BGP 的 Weight 在 BGP 候选路径之间比较；管理距离在同一前缀的不同协议来源之间比较。直连恢复后 OSPF 路由能否重新进入 IP 路由表，取决于后者。

修复目标为 OSPF 距离 110 优先于 eBGP 距离 115，并保留断链时的既有隔离保护。管理距离只影响本机路由选择，不会撤销对端通告，也不改变 AS_PATH。

直连正常时，r11 将 OSPF 路由重分发进 BGP，本地产生的路径具有 32768 的 Weight。两条 HQ—DC 直连都断开后，这条本地路径撤销，SP 学到的 eBGP 路径以默认管理距离 20 进入路由表。直连恢复时，OSPF 的管理距离 110 无法替换它，本地重分发路径也无法按正常状态重建，因而出现此前依赖手工清除 BGP 的恢复方式。

在 r11 的 IPv4 地址族新增管理距离配置，使 OSPF 110 优先于 eBGP 115；iBGP 和本地产生路由保持 200。此处改变协议之间的路由表选择，不修改 AS_PATH、邻居协议或 IPv6 地址族。

```text
configure terminal
router bgp 65001
 address-family ipv4
  distance bgp 115 200 200
end
write memory
```

实际配置输出。管理距离配置作用于 r11 整个 IPv4 BGP 地址族，因此同时检查传统分支和 IaaS 的既有路径；不能只看一条 DC 路由。

| --- | --- | --- |
| sw101、sw102 的 Ethernet0/2 同时 shutdown | r11 的 DC 路由转为 BGP，距离 115；以 r11 Loopback 为源到 DC 0/3 | 断链路由及探测 |
| DC 反向探测 r11 Loopback | 0/3，未经 SP 绕通企业地址 | 反向探测 |

| 检查 BGP 邻居 | 会话持续运行，整个修复与本次故障恢复未执行 clear ip bgp | 下图及恢复日志 |

### AS_PATH 过滤对照验证

为核对额外 HQ-NO-SP 出方向前缀过滤是否必要，临时从 r21 的 100.3.21.1、r22 的 101.22.0.1 邻居移除该绑定，保留 AS_PATH 入方向过滤。正常状态 r11 经两条 HQ 直连使用 OSPF 110，到 DC 10.2.255.211 为 3/3。

关闭 sw101、sw102 Ethernet0/2 后，r11 仍有经 100.3.11.1 的 BGP 115 DC 路由；r21、r22 均没有 10.1.255.11 路由。HQ→DC、两台 DC→HQ 的 Loopback 源探测均为 0/3。该结果只能说明被测双向通信不通，不能证明没有单向请求经过 SP，也不足以把“所有通信只能经直连”判为完全满足。

测试结束已恢复两条 Ethernet0/2 和原 HQ-NO-SP 邻居绑定，并保存 r21、r22。r11 自动恢复 OSPF 110、两条 HQ 下一跳，重新探测为 3/3，没有执行 clear ip bgp。验证范围为上述源、目的及操作条件；单向转发路径仍缺独立证据。

证据：r11 断链、r21 断链、r22 断链、r11 恢复、r21 策略恢复、r22 策略恢复。

### HQ 入方向补充过滤与断链抓包

现有 DC 入方向过滤拒绝包含 AS 65001 的路径，但它不会阻止 HQ 接收 AS 65002 的 DC 路由。双直连断开时，原配置仍允许 HQ 把请求发往 SP；此前仅凭双向 ping 不通不足以关闭这个问题。

在 r11 的 IPv4 地址族新增 AS_PATH 过滤，拒绝包含 DC AS 65002 的路径，其余允许。仅做 soft in 路由刷新，没有重置 BGP 会话；IPv6 地址族未绑定这个过滤器。保留 DC 原有入方向过滤和出方向前缀保护。

```text
configure terminal
ip as-path access-list 20 deny _65002_
ip as-path access-list 20 permit .*
router bgp 65001
 address-family ipv4
  neighbor 100.3.11.1 filter-list 20 in
end
clear ip bgp 100.3.11.1 soft in
write memory
```

**题面与实施差异：**原书参考答案同样使用了 DC 出方向前缀列表。此处增加 HQ 入方向过滤是针对实际转发漏洞的实验修正，超出题面“在 r21、r22 完成过滤”的位置限制。没有将它标为严格符合全部题面限制的唯一解法。AS_PATH 经过 OSPF 重分发后会丢失原来源，不能仅凭空 AS_PATH 区分总部与数据中心的本地重分发前缀；笼统拒绝所有本地路由还会影响其他站点。

### PAT 配置

PAT 将内部源地址转换为出口地址，并使用端口或 ICMP 标识区分会话。标准 ACL `NAT` 选择需要转换的源地址范围；`ip nat inside/outside` 标记内外接口；`overload` 允许多个内部会话共用一个出口地址。

转换表中的 Inside local 为内部原始地址，Inside global 为出口转换地址。NAT 命中计数及实际转换条目与终端探测结合，确认本次流量使用的出口。

三台出口均配置：

```text
ip access-list standard NAT
 permit 10.0.0.0 0.255.255.255
!
interface Ethernet0/0
 ip nat outside
interface Ethernet0/1
 ip nat inside
interface Ethernet0/2
 ip nat inside
interface Ethernet0/3
 ip nat inside
!
ip nat inside source list NAT interface Ethernet0/0 overload
```

实际已连接的内侧接口参与转发；e0/3 在 r23/r24 当前未有有效业务邻接，保留 inside 不等于已验证该链路。

核心规则为 `ip nat inside source list NAT interface Ethernet0/0 overload`：ACL NAT 选择源地址，Ethernet0/0 提供转换后的地址，overload 使用端口或 ICMP 标识区分会话。ACL 中 `permit 10.0.0.0 0.255.255.255` 匹配 `10.0.0.0/8`，包含 host11 的 `10.1.100.101`；截图计数为100 matches，是该 ACL 累计匹配值，并非本次30个 ping 的统计。

另一条带 `vrf Guest` 的 NAT 规则用于独立 Guest 转发域，属于 G5 访客出口配置，不表示 host11 经过两次转换。这里的 ACL 用于选择 NAT 源地址，不能单独当作接口访问控制策略。筛选 `include ip nat` 会丢失接口上下文，因此单凭筛选输出中的 inside/outside 行无法逐项确认接口归属。

![r23 的企业 PAT、Guest PAT 与源地址匹配范围](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/710edeae88fe483d9870.png)

## 项目补充：总部、数据中心与 IaaS 动态互联

### 地址与协议边界

保留课程 HQ—IaaS 的 IPv6 VPNv6 实验，另在同一条 r4—r30 链路增加 IPv4 BGP，使数据中心和总部都能访问模拟云侧服务。r30-IOL-IPv6 沿用原节点名，现在同时承载 IPv4 和 IPv6；无需新建云平台。

| 位置 | 设备与 AS | 地址及职责 |
|---|---|---|
| 总部 | r11，AS65001 | 接 SP1 r3；总部用户网为 10.1.100.0/24、10.1.101.0/24 |
| 数据中心 | r21/r22，AS65002 | r21 接 SP1 r3，向 OSPF 发布云侧 BGP 路由；服务目标 sw211 为 10.2.255.211 |
| 运营商 | r3/r4，AS10000 | MPLS VPNv4 承载，r3 使用 fabd2，r4 使用 giosk |
| IaaS | r30，AS65003 | e0/0=100.4.30.2/30，对端 r4 e0/1=100.4.30.1/30；Loopback100=10.3.100.10/32 模拟服务地址 |

数据中心到云侧的逻辑路径为 `DC → r21 → r3 → SP1 MPLS 核心 → r4 → r30`。总部可沿已有 HQ—DC OSPF 路径转到 r21；r11 也保留运营商 BGP 路径。AS_PATH 表示跨自治系统传播关系，不代替内部逐跳转发轨迹。

### 云侧 IPv4 BGP

r30 在已有 e0/0 上增加 IPv4 地址，保留 IPv6 地址及邻居：

```text
interface Ethernet0/0
 ip address 100.4.30.2 255.255.255.252
interface Loopback100
 description Simulated-IaaS-Service
 ip address 10.3.100.10 255.255.255.255
router bgp 65003
 neighbor 100.4.30.1 remote-as 10000
 address-family ipv4
  network 10.3.100.10 mask 255.255.255.255
  neighbor 100.4.30.1 activate
```

r4 的 giosk VRF 增加云侧邻居，导出 RT10000:3682。r3 的 fabd2 IPv4 地址族导入该 RT，使总部和 DC 的 CE 学到云侧前缀。

```text
! r4
interface Ethernet0/1
 ip address 100.4.30.1 255.255.255.252
router bgp 10000
 address-family ipv4 vrf giosk
  neighbor 100.4.30.2 remote-as 65003
  neighbor 100.4.30.2 activate
!
vrf definition giosk
 address-family ipv4
  route-target both 10000:3682
!
! r3
vrf definition fabd2
 address-family ipv4
  route-target import 10000:3682
```

回程在 r4 导入企业 RT10000:1，并用 import map 仅允许总部、DC 地址范围。其他分支前缀不因这项云侧扩展直接导入 giosk。

```text
ip prefix-list CLOUD-IMPORT permit 10.1.0.0/16 le 32
ip prefix-list CLOUD-IMPORT permit 10.2.0.0/16 le 32
route-map CLOUD-IMPORT permit 10
 match ip address prefix-list CLOUD-IMPORT
vrf definition giosk
 address-family ipv4
  import map CLOUD-IMPORT
  route-target import 10000:1
end
write memory
```

最初仅有云侧去程路由，r30 没有企业回程，ping 不通。补上上述受控导入后互通正常。最终配置以本节和配置快照为准。

## ERP 云侧业务接入与迁移

云侧新增实际运行的 Python HTTPS 订单服务和 SQLite 数据库，使用三条模拟订单演示迁移。服务运行在 EVE 主机的 Linux network namespace，通过 veth 接入课程网络；没有额外启动大型虚拟机。它是轻量模拟 ERP 业务，不是完整 ERP 产品。

| 位置 | 服务地址 | 网关及实际接口 | EVE 网络 |
|---|---|---|---|
| 数据中心 | 10.2.100.20/24 | sw211 e2/0，10.2.100.1 | DC-ERP-Linux，63 |
| IaaS | 10.3.101.20/24 | r30 e0/1，10.3.101.1 | Cloud-ERP-Linux，64 |
| 总部客户端 | 10.1.101.110/24 | 10.1.101.1 | 原 VLAN2001，2 |

sw211 的 e2/0 配置三层地址并加入 OSPF 1 area 0；r30 在 BGP AS65003 发布云侧 /24。r4 的 CLOUD-IMPORT 追加 10.4.200.0/24 和 10.6.0.0/16，分别提供 SD-WAN、DMVPN 返回路径。

```text
! sw211
interface Ethernet2/0
 no switchport
 ip address 10.2.100.1 255.255.255.0
 ip ospf 1 area 0
 no shutdown
! r30
interface Ethernet0/1
 ip address 10.3.101.1 255.255.255.0
 no shutdown
router bgp 65003
 address-family ipv4
  network 10.3.101.0 mask 255.255.255.0
! r4
ip prefix-list CLOUD-IMPORT permit 10.4.200.0/24
ip prefix-list CLOUD-IMPORT permit 10.6.0.0/16
```

迁移使用 SQLite backup 接口将 DC 数据库复制到云侧，核对排序后的订单内容摘要。随后 DC 原地址作为 HTTPS 转发入口，客户端保持原 URL，后端改为云侧。该只读订单实验不涉及生产写入同步。

| 检查 | 实际结果 |
|---|---|
| 迁移前总部访问 DC | HTTPS 200，backend=dc，3 条订单 |
| 数据迁移 | DC/云侧均 3 条，SHA-256 一致 |
| 迁移后总部使用原地址 | HTTPS 200，backend=cloud，entrypoint=dc-stable-url |
| 无认证请求 | HTTP 401 |

订单摘要：`b7569e248fca528bf6206b7f3452e1b6b1fa6185a789bb24e51bc38c3b5fbb84`。
