记录日期：2026-10-25｜实验：G0-IOL-Basic

本实验从一台路由器开始，逐步增加到四台，依次配置接口地址、静态路由、OSPF 和 BGP。每增加一部分，先看现有配置还缺少哪条路径，再通过配置和路由表检查让对应地址互通。

实验使用 EVE 中的 Cisco IOL 虚拟路由器。EVE 提供画布、连线和开关机；真正处理 IP 地址、路由和报文的是里面的 IOS 设备。网页能打开，只说明管理页面可访问；实验里的路由器能否通信，还要检查它们自己的接口和路由。

八部分沿用同一个 `G0-IOL-Basic` 实验，配置逐步累积。第二部分沿用第一部分的 R1，第四部分会删除第三部分的静态路由，第五部分再增加 R3。各部分的复现基线为上一部分结束时的配置；最终四路由器状态与早期配置片段存在差异。

| 实验阶段 | 核心内容 | 验证依据 |
| --- | --- | --- |
| 一台 R1 | 运行配置、启动配置与重启保留 | 运行配置、启动配置、重启后的接口 |
| R1—R2 直连 | 接口启用与直连通信 | up/up、直连路由、双向 ping |
| 两台的 Loopback | 远端 Loopback 的双向静态路由 | 双向静态路由、指定源地址的 ping |
| 换成 OSPF | OSPF 邻居与前缀发布 | FULL 邻居、O 路由 |
| 增加 R3 | 协议边界与受控路由交换 | B 路由、OSPF 外部路由、端到端 ping |
| 关闭并恢复链路 | 故障后的路由撤销与恢复 | 邻居变化、路由撤销与恢复 |
| 发布临时地址 | 允许前缀与拒绝前缀对照 | R2 收到、R1 没收到，正常路由仍在 |
| 增加 R4 | 新增 AS 与云侧前缀放行 | BGP 路径、白名单、总部与云侧双向 ping |

## EVE 环境与配置保存

### 接口、地址与配置基础

路由器根据目的 IP 地址查询路由表，选择下一跳及出接口。本节完成设备命名、Loopback 地址配置和配置保存，作为后续互联实验的基础。

`Ethernet0/0` 是可接线的以太网接口，名称中的数字用于定位接口。`Loopback0` 是在设备内部创建的逻辑接口，不需要接网线；后面用它作为稳定的测试目标，避免把“能 ping 通旁边的网口”误当成“已经能访问远端网络”。Loopback 的 up/up 只说明本机接口正常，不能证明别人已经有到它的路由。

地址后面的 `/32` 表示网络前缀长度为 32 位，对应掩码 `255.255.255.255`，在这里代表一个 IPv4 主机地址。第二部分会使用 `/30`，让两个相邻接口处在同一子网。

### 启动与基础配置

右键路由器选择 `Start`，双击节点打开 HTML5 控制台。首次启动的初始配置向导输入 `no`，按回车进入 CLI。

![路由器首次启动并进入 Router 提示符](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/9b2016ddd64433996d57.png)

CLI 的提示符对应当前命令模式：`Router>` 为用户模式，执行 `enable` 后进入特权模式 `Router#`；`configure terminal` 进入全局配置模式。`end` 返回特权模式。

配置起点为 `Router>`。命令块不含提示符，缩进对应上一行进入的配置范围。

| 命令或提示符 | 含义 |
| --- | --- |
| `enable` → `Router#` | 进入特权模式，可以查看状态、进入配置和保存 |
| `configure terminal` → `(config)#` | 进入全局配置模式 |
| `hostname R1` | 把设备内部名称改成 R1，方便确认正在操作谁 |
| `interface Loopback0` → `(config-if)#` | 创建或进入 Loopback0，之后的地址命令作用于该接口 |
| `ip address ...` | 配置接口的 IPv4 地址和掩码 |
| `end` → `R1#` | 结束配置，返回特权模式；这一步不保存配置 |
| `show ip interface brief` | 简要列出接口、IP 地址及状态 |

配置主机名和 Loopback0：

```text
enable
configure terminal
hostname R1
interface Loopback0
 ip address 10.255.0.1 255.255.255.255
end
show ip interface brief
```

`hostname` 修改设备内部主机名，EVE 画布上的节点标签单独设置。Loopback0 是逻辑接口，无需连接其他设备；本次用它检查配置保存后能否在重启时重新加载。

配置后提示符为 `R1#`。`show ip interface brief` 中，Loopback0 的 `IP-Address` 为 `10.255.0.1`，`Status`、`Protocol` 均为 `up`，即 up/up。

未使用的 Ethernet 接口保持 `administratively down`，表示接口在配置上被关闭，并非 Loopback 配错。后面接线时再用 `no shutdown` 启用相应物理接口。

![主机名和 Loopback0 运行状态](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/c72de71183423f6aa5bb.png)

### 保存配置

IOS 接受配置命令后，会立即修改 `running-config`（当前运行配置），不必等保存才生效。`startup-config`（启动配置）是设备启动时读取的内容。只修改运行配置而没有保存，重新启动后可能回到旧设置。

保存的方向是“把当前运行配置复制到启动配置”，在 `R1#` 下执行：

```text
copy running-config startup-config
```

出现 `Destination filename [startup-config]?` 时直接回车。返回 `[OK]` 后，检查保存内容：

```text
show startup-config | include ^hostname
show startup-config | section ^interface Loopback0
```

输出包含 `hostname R1`，以及 Loopback0 下的 `ip address 10.255.0.1 255.255.255.255`。

![保存成功并核对启动配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/79cbe4a7f68bb325d392.png)

`show startup-config | include ^hostname` 只显示以 hostname 开头的行；`| section ^interface Loopback0` 显示 Loopback0 的配置段。竖线后的内容用于筛选输出，便于核对，不会修改设备。

### 停止并重新启动验证

1. 返回拓扑，右键路由器选择 `Stop`。
2. 停止后选择 `Start`，重新打开控制台。此处使用普通停止和启动；`Wipe` 会清除节点状态。
3. 进入特权模式，检查接口、运行配置和启动配置：

```text
show ip interface brief
show running-config | include ^hostname
show startup-config | section ^interface Loopback0
```

重新启动后，主机名仍为 `R1`，Loopback0 地址仍为 `10.255.0.1/32`，状态为 `up/up`，启动配置保留相同地址。

![停止并重新启动后的配置保留](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/d080caa615affa6f1594.png)

接口的 `Method` 从 `manual` 变为 `NVRAM`，对应从已保存配置加载地址。

## 两台路由器直连互通

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 拓扑与地址

上一部分只检查了 R1 自己的配置，现在增加 R2，让两台设备真正交换报文。两端 Ethernet0/0 接在同一条链路上，配置同一子网中的不同地址，就能先验证最基本的相邻通信。


`10.12.0.0/30` 为 R1—R2 直连网段。R1 的 Loopback 暂时保留，当前先测试两个 Ethernet 地址。

![R1 与 R2 已添加，尚未连接](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/5a66c6ff003efc99b031.png)

| 设备 | 接口 | 地址 |
| --- | --- | --- |
| R1 | Ethernet0/0 | 10.12.0.1/30 |
| R2 | Ethernet0/0 | 10.12.0.2/30 |
| R1 | Loopback0（沿用） | 10.255.0.1/32 |

`10.12.0.0/30` 中，.0 是网络地址，.1、.2 可分配，.3 是广播地址。两端属于同一子网，接口启用后形成直连路由，无需配置路由协议。

### 连接设备

保存 R1 配置并停止两台节点。从 R1 的连接图标拖到 R2，两端选择 `Ethernet0/0`，保存连线。

![两端选择 e0/0](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/5de33cfc9d32a38cef52.png)

![连接已保存，两台节点处于停止状态](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/1617941821d3e0304313.png)

### 配置接口

启动两台设备并打开控制台。R2 首次启动时跳过初始配置向导。以下 R1 命令从 `R1#` 开始；若看到 `R1>`，先执行 `enable`。后续部分同样以设备的特权模式为配置起点。

接口配置包含地址、掩码和启用状态。`255.255.255.252` 对应 `/30`，两端地址属于同一子网；`no shutdown` 解除接口的管理关闭状态。

R1：

```text
configure terminal
interface Ethernet0/0
 ip address 10.12.0.1 255.255.255.252
 no shutdown
end
show ip interface brief
```

![R1 Ethernet0/0 地址与状态](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/053790cc6593ebed3307.png)

R2：

```text
enable
configure terminal
hostname R2
interface Ethernet0/0
 ip address 10.12.0.2 255.255.255.252
 no shutdown
end
show ip interface brief
```

![R2 Ethernet0/0 地址与状态](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/0ab2a85dadd001ed490b.png)

`no shutdown` 启用接口。两端 Ethernet0/0 均为 `up/up`；R1 原有 Loopback0 保持不变。`Ctrl+Z` 和 `end` 都可返回特权模式，本身不保存配置。

接口正常后，路由器会自动把它所在的网段放入路由表，这叫直连路由。这里不用手写 `ip route`，因为设备已经知道 `10.12.0.0/30` 就连接在自己的 Ethernet0/0 上。

### 检查直连路由与通信

R1：

```text
show ip route connected
ping 10.12.0.2
```

R2：

```text
show ip route connected
ping 10.12.0.1
```

两端的 `show ip route connected` 均包含 `C 10.12.0.0/30`，出接口为 Ethernet0/0。`C`（Connected）表示直接连接的网段；`L`（Local）表示本机接口地址的 /32 本地路由。去往 `10.12.0.2` 的报文在 R1 匹配直连网段，直接从这条链路发送。

`ping` 发送 ICMP Echo 请求，目标收到后返回应答。IOS 输出中的 `!` 表示收到应答，`.` 表示等待超时；5/5 表示本次发出的 5 个请求都收到应答。默认路由用于没有更具体路由的目的地，本节的直连通信不依赖它。

R2 到 R1 为 5/5；R1 首次为 4/5，首包超时。

![R2 的直连路由与 ping 结果](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/96b405f875fdb1587b61.png)

![R1 的直连路由与首次 ping 首包超时](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/54e804c78dc333979e1f.png)

R1 重测为 5/5。`show ip arp` 显示 10.12.0.2 对应 MAC `aabb.cc00.2000`，接口为 Ethernet0/0。首次超时可能与 ARP 解析有关，本次未抓包确认原因。

![R1 重测成功及对端 ARP 映射](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/f366219864fd6cf9cae9.png)

直连通信的常见故障及核对项：

| 故障现象 | 核对项 |
| --- | --- |
| `administratively down` | 是否在接线对应的接口执行了 `no shutdown` |
| 接口未到 up/up | 两台节点是否运行、连线两端是否选对接口 |
| 接口 up/up，但地址不对 | 是否把命令输入到了正确设备和接口，地址与掩码是否一致 |
| 没有 `C 10.12.0.0/30` | 接口状态和掩码是否正确 |
| 直连路由正常，ping 仍失败 | 目标地址是否正确，检查 `show ip arp` 的邻居解析情况 |

## 双向静态路由访问 Loopback

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 地址与双向路径

沿用上一部分的直连链路和已保存地址，在 R2 新建 `10.255.0.2/32` 的 Loopback0。此时 R1 认识自己的 Loopback 和两台之间的 `10.12.0.0/30`，却没有理由自动知道 R2 内部还有一个 `10.255.0.2`。物理线接通，只解决了相邻接口的通信；访问远端地址还需要路由。


静态路由手工指定目的前缀和下一跳。去程由 R1 指向 R2 的 Loopback，回程由 R2 指向 R1 的 Loopback；指定源地址的 ping 同时依赖这两个方向。

| 设备 | Loopback0 | 远端目的 | 下一跳 |
| --- | --- | --- | --- |
| R1 | 10.255.0.1/32 | 10.255.0.2/32 | 10.12.0.2 |
| R2 | 10.255.0.2/32 | 10.255.0.1/32 | 10.12.0.1 |

静态路由写法为 `ip route 目的网络 掩码 下一跳`。下一跳使用相邻路由器的直连接口地址；/32 精确匹配一个 IPv4 地址。通信需要去程和回程都有路由。

以 R1 的命令为例：


R1 的下一跳为直连可达的 R2 接口 `10.12.0.2`，远端目标为 `10.255.0.2/32`。配置命令如下。

### 配置 Loopback 与静态路由

R2：

```text
configure terminal
interface Loopback0
 ip address 10.255.0.2 255.255.255.255
exit
ip route 10.255.0.1 255.255.255.255 10.12.0.1
end
```

![R2 配置 Loopback 与静态路由](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/ae51b22fd79e576f1cb7.png)

R1：

```text
configure terminal
ip route 10.255.0.2 255.255.255.255 10.12.0.2
end
```

### 验证与保存

R1：

```text
show ip route static
ping 10.255.0.2 source 10.255.0.1
```

R2：

```text
show ip route static
ping 10.255.0.1 source 10.255.0.2
```

指定 Loopback 为源地址，可以同时检查两个 Loopback 之间的去程和回程。普通 ping 可能使用出接口 10.12.0.x 为源，回程只需直连路由，无法完成相同的验证。

| 设备 | 静态路由 | 指定源地址 ping |
| --- | --- | --- |
| R1 | `S 10.255.0.2/32 [1/0] via 10.12.0.2` | 5/5 |
| R2 | `S 10.255.0.1/32 [1/0] via 10.12.0.1` | 5/5 |

R1 到 `10.255.0.2/32` 的路由来源为静态配置，下一跳为 `10.12.0.2`。`S`（Static）表示静态路由，`[1/0]` 分别为管理距离和度量值。管理距离用于比较不同路由来源对同一前缀的可信程度，通常数值越小越优先；它不是 ping 的时延。

指定源地址后，请求从 R1 的 `10.255.0.1` 发出，R2 必须能把应答送回这个地址。若单纯 ping `10.12.0.2` 成功，而这个指定源测试失败，应重点检查两个 Loopback 地址和双向静态路由，而不是立即重配物理链路。

两台执行 `copy running-config startup-config`，均返回 `[OK]`。

## 使用 OSPF 自动学习 Loopback 路由

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 拓扑与原理

静态路由可以解决两台设备的问题，但每增加一个远端网段，都需要手动维护相应路径。本节保持接口、连线和 IP 地址不变，把两条静态路由换成 OSPF，让两台设备交换路由信息。

OSPF（开放最短路径优先）是内部网常用的动态路由协议。两台设备先在互联接口上发现彼此并建立邻居，交换链路状态信息，再各自计算路径，把选中的路由装入自己的路由表。配置了 OSPF 进程并不代表邻居一定建立；邻居正常也不代表所有需要的接口网段都已经发布。

| 设备 | Ethernet0/0 | Loopback0 | Router ID |
| --- | --- | --- | --- |
| R1 | 10.12.0.1/30 | 10.255.0.1/32 | 1.1.1.1 |
| R2 | 10.12.0.2/30 | 10.255.0.2/32 | 2.2.2.2 |

OSPF 进程号 `1` 在本机有效。Router ID 标识路由器，不会创建接口。两个接口都加入 area 0；Loopback 发布地址，Ethernet0/0 建立邻居。

先删除静态路由，因为静态路由默认管理距离为 1，低于 OSPF 的 110，保留它会使路由表继续优选静态路径。

本节的配置要区分三件事：

| 配置对象 | 本实验设置 | 作用 |
| --- | --- | --- |
| OSPF 进程 | `router ospf 1` | 创建本机进程；数字 1 是本机进程编号 |
| 路由器标识 | `router-id 1.1.1.1` 或 `2.2.2.2` | 用唯一 ID 区分两台路由器，不会为设备新增这个 IP 地址 |
| 接口所属区域 | `ip ospf 1 area 0` | 把接口加入该进程的骨干区域 area 0，两端互联口区域一致 |

`passive-interface default` 让接口默认不发送 OSPF Hello、不建立邻居；用 `no passive-interface Ethernet0/0` 仅放开需要交换路由的互联口。Loopback 不接另一台设备，保持被动即可，它的前缀仍能由 OSPF 发布。

### 配置 OSPF

R1：

```text
configure terminal
no ip route 10.255.0.2 255.255.255.255 10.12.0.2
router ospf 1
 router-id 1.1.1.1
 passive-interface default
 no passive-interface Ethernet0/0
exit
interface Ethernet0/0
 ip ospf 1 area 0
exit
interface Loopback0
 ip ospf 1 area 0
end
```

![R1 修正被动接口并加入 OSPF](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/bc2065835e1ff0aa7cd8.png)

R2：

```text
configure terminal
no ip route 10.255.0.1 255.255.255.255 10.12.0.1
router ospf 1
 router-id 2.2.2.2
 passive-interface default
 no passive-interface Ethernet0/0
exit
interface Ethernet0/0
 ip ospf 1 area 0
exit
interface Loopback0
 ip ospf 1 area 0
end
```

![R2 OSPF 配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/f1a3e39417cdb8451aeb.png)

`passive-interface default` 默认禁止接口建立邻居；`no passive-interface Ethernet0/0` 放开互联口。被动 Loopback 仍可发布其网段。

### 邻居与路由验证

两台执行：

```text
show ip ospf neighbor
show ip route ospf
```

R2 的实际邻居状态为 `FULL/DR`，`FULL` 表示邻接已完成数据库同步。`Neighbor ID` 为 `1.1.1.1`，是 R1 的 Router ID；邻居接口地址为 `10.12.0.1`，两者用途不同。

`/DR` 表示对端 R1 在这个以太网网段的指定路由器角色，后续记录也可能出现 `/BDR`。本节重点是 FULL 和正确的邻居、接口，不要求每次启动后都由同一台担任 DR。

R2 学到 `O 10.255.0.1/32 [110/11] via 10.12.0.1`。与上一节的 `S` 对照，这里的 `O` 表示 OSPF 区域内路由；目的仍是 R1 的 Loopback，下一跳仍是 R1 的直连接口。

`110` 是 OSPF 默认管理距离，`11` 是本次路径的 cost（开销）。cost 用于 OSPF 内部比较路径，不是接口速率或通信耗时。看到目的路由从 S 变成 O，才能确认当前使用的是 OSPF 学到的路由；单看 ping 成功无法区分它是否仍在走旧静态路由。

重复删除已不存在的静态路由会提示 `%No matching route to delete`，无需重新添加再删除。IOS 按已接受的命令即时修改运行配置，中途退出不会撤销整段配置。

## 三路由器 OSPF 与 BGP 分层互联

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 拓扑与地址

前面两台处在同一个 OSPF 网络中。现在增加 R3，把 R1、R2 所在的总部与一个模拟数据中心连接起来：总部内部继续用 OSPF，R2 与 R3 之间改用 eBGP。

BGP（边界网关协议）在这里用于两个自治系统之间交换路由。AS 是自治系统的编号，本实验的总部使用 AS65001，模拟数据中心使用 AS65002；这些是实验使用的私有 AS 号。不同 AS 之间的 BGP 邻居叫 eBGP。本节只在 R2 和 R3 上配置 BGP，R1 仍然只运行 OSPF。

R2 因而承担两种职责：向 R1 交换 OSPF 路由，向 R3 交换 BGP 路由。两套协议默认不会因为运行在同一台设备上，就自动把各自学到的所有路由告诉另一套协议。

```text
R1 e0/0 —— e0/0 R2 e0/1 —— e0/0 R3
       OSPF area 0          eBGP
       总部 AS65001         DC AS65002
```

| --- | --- | --- |
| R2 | Ethernet0/1 | 10.23.0.1/30 |
| R3 | Ethernet0/0 | 10.23.0.2/30 |
| R3 | Loopback0 | 10.255.0.3/32 |

```text

end
```

R3：

```text
configure terminal

end
```

![R3 BGP配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/a1571c1bf78207b9f2d0.png)

以 R2 的配置为例，`router bgp 65001` 声明本机 AS；`neighbor 10.23.0.2 remote-as 65002` 声明对端地址和对端 AS。R3 要反向配置 R2 的地址 `10.23.0.1` 和 AS65001，不能把本机地址写成邻居。

`network 10.255.0.2 mask 255.255.255.255` 表示将这个精确前缀发给 BGP 邻居。该命令用于发起前缀通告，接口创建和接口地址配置独立完成。本地 IP 路由表必须已经存在目的前缀及掩码完全匹配的路由；此处来自 R2 自己的 Loopback。

| R3 | `B 10.255.0.2/32 [20/0] via 10.23.0.1` | 到 10.255.0.2：5/5 |

20 为 eBGP 默认管理距离。两端保存均返回 `[OK]`。

此阶段完成 R2 与 R3 的 Loopback 互通。R1 到 R3 仍缺少两个方向的路由：R1 的 OSPF 中缺少 R3 Loopback，R3 的 BGP 中缺少 R1 Loopback。

### 在 R2 控制 OSPF 与 BGP 的路由交换

R2 同时运行两种协议，不会自动互相传递路由。本次分别处理两个方向：

- 总部到 DC：用 BGP `network` 精确发布由 OSPF 学到的 10.255.0.1/32。
- DC 到总部：用 prefix-list 和 route-map，仅将 10.255.0.3/32 从 BGP 重分发到 OSPF。


路由信息分别从 OSPF 和 BGP 传播到协议边界；业务报文按路由从 R1 经 R2 到 R3，应答沿反方向返回。

R2 的三个配置对象要配合使用：`prefix-list` 挑出允许的目的前缀；`route-map` 引用这个列表形成策略；OSPF 下的 `redistribute` 才真正把 BGP 路由按策略引入 OSPF。只创建列表和策略而没有应用，不会改变路由传播。

R2：

```text
configure terminal
ip prefix-list DC-LOOPBACK seq 10 permit 10.255.0.3/32
route-map BGP-TO-OSPF permit 10
 match ip address prefix-list DC-LOOPBACK
exit
router ospf 1
 redistribute bgp 65001 subnets metric 20 metric-type 1 route-map BGP-TO-OSPF
exit
router bgp 65001
 network 10.255.0.1 mask 255.255.255.255
end
```

![R2精确前缀路由交换配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/7974039d91539a14c45c.png)

prefix-list 未指定 `ge/le` 时精确匹配前缀长度。route-map 仅包含该 permit 条目，其他前缀不会通过此次重分发。`metric-type 1` 使用 OSPF E1，总代价包含外部度量和到边界路由器的内部开销。

`redistribute bgp 65001` 中的 65001 是 R2 的本机 BGP AS，不是对端 R3 的 65002。`subnets` 允许引入子网路由；`metric 20` 为引入路由设置外部开销；`route-map BGP-TO-OSPF` 将引入范围限制到策略匹配的前缀。

本节用 `network` 向 BGP 发布 R1 的精确 Loopback，用受限重分发把 R3 的 Loopback 引入 OSPF。这里不需要把全部 OSPF 和 BGP 路由双向引入，否则会扩大传播范围，也增加后续控制和排错的难度。

## BGP 链路故障与路由撤销恢复

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 测试链路

沿用上一部分的配置，先确认 R1 到 R3 的指定源 ping 正常，再关闭 R2 的 Ethernet0/1。这个接口只连接 R3，不是连接 R1 的 Ethernet0/0，操作前先核对设备名和接口名。


本拓扑只有这一条去 R3 的路径，因此断链期间预期会中断通信。要观察的是：R2 失去 BGP 路由后，是否也停止向内部 OSPF 发布该目标；链路恢复后，路由和通信是否一起恢复。这是故障传播与恢复实验，还没有备用链路可供切换。

| 观察位置 | 断链后应关注的变化 |
| --- | --- |
| R2 接口和 BGP 邻居 | 接口被关闭，R3 邻居离开已建立状态 |
| R2 路由表 | 从 R3 学到的 `10.255.0.3/32` 撤销 |
| R1 OSPF 邻居 | 到 R2 的内部邻接仍在 |
| R1 路由与 ping | 外部路由撤销，到 R3 的指定源 ping 失败 |

### 关闭接口并检查撤路

R2：

```text
configure terminal
interface Ethernet0/1
shutdown
end
show ip bgp summary
show ip route 10.255.0.3
```

邻居因 Interface flap 进入 Idle，10.255.0.3/32 返回 `Subnet not in table`。

![R2接口关闭后BGP断开与路由撤销](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/b35cfa8fc10491c17b33.png)

R1：

```text
show ip ospf neighbor
show ip route 10.255.0.3
ping 10.255.0.3 source 10.255.0.1
```

R1—R2 的 OSPF 邻居保持 FULL/BDR，但到 10.255.0.3 的外部路由消失，ping 为 0/5。这表明外部链路故障通过路由撤销影响了内部业务，内部 OSPF 邻接仍正常。

![R1内部OSPF邻居正常而外部路由撤销](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/b1103ab8a7b5b6e221cc.png)

`Subnet not in table` 表示当前查询目标没有对应路由。它与“接口坏了”不是同一个结论：R1 到 R2 的 OSPF 邻居仍为 FULL，说明内部链路还工作，但已经没有到外部目标的路径。

`shutdown` 是主动制造故障，先完成观察，再按下一步执行 `no shutdown` 恢复。故障状态不保存到启动配置。

### 测试结果

外部链路故障后，R2 撤销 BGP 路由，R1 撤销相应 OSPF 外部路由；接口恢复后，邻居与双向业务恢复。最终 R2 路由表未另截图，恢复由 R3 邻居日志及两端路由、ping 结果确认。

本次未运行连续业务探测，未量化收敛时间。

## OSPF 重分发前缀过滤验证

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 过滤位置

第五部分只允许 `10.255.0.3/32` 从 BGP 进入 OSPF。只看到这条路由能通过，还无法说明其他路由会被拒绝。现在从 R3 临时发布 `10.255.99.3/32`，让它走到同一个过滤位置，再对照检查。


过滤点在 R2 从 BGP 引入 OSPF 的位置，所以 R2 应能收到测试路由，R1 才应收不到。若 R2 本身都没收到，就不能拿 R1 没有这条路由来证明过滤成功。

### 发布测试前缀

R3：

```text
configure terminal
interface Loopback99
ip address 10.255.99.3 255.255.255.255
exit
router bgp 65002
network 10.255.99.3 mask 255.255.255.255
end
```

![R3发布测试前缀](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/996cee3a60609d21a825.png)

### 检查边界与下游路由

R2：

```text
show ip route 10.255.99.3
```

R2 已通过 BGP 收到该前缀，下一跳 10.23.0.2，说明测试路由到达了重分发边界。

![R2实际收到测试BGP路由](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/62f80e3562f3cc2aa06d.png)

R1：

```text
show ip route 10.255.99.3
show ip route 10.255.0.3
```

测试前缀返回 `Subnet not in table`，允许的 10.255.0.3/32 仍为 OSPF E1，metric 30。正向路由保留、负向路由被过滤。

![R1未收到测试前缀而允许前缀保留](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/632a78d5091ebc3ba8fa.png)

R2 输出中的 `Redistributing via ospf 1` 不能单独证明某条路由已通过 route-map；需结合下游路由检查。本次检查范围为路由表，未另查外部 LSA。

这个对照同时检查两件事：不允许的路由没有进入总部，原来允许的路由没有被误删。仅检查“坏路由没了”，可能掩盖整条邻接中断或所有路由都被挡住的问题。

### 清理与业务回归

R3：

```text
configure terminal
router bgp 65002
no network 10.255.99.3 mask 255.255.255.255
exit
no interface Loopback99
end
```

![R3清理临时配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/891393d868e78df382ac.png)

R1 执行 `ping 10.255.0.3 source 10.255.0.1`，结果为 5/5。

![原业务ping回归成功](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/a0c9b3a816ac5548a1c2.png)

R2 重查测试前缀，返回 `Subnet not in table`，确认临时路由已撤销。

![R2确认测试路由已撤销](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/de0e45824fa5c5c28e5e.png)

清理时先撤掉 BGP 的 `network`，再删除临时 Loopback99。最后既检查 R2 已无测试路由，也检查原有 `10.255.0.3/32` 的通信仍正常，避免把测试配置留给下一部分。

三台运行配置已采集并核对：R3 无临时 Loopback99 和对应 network，三台无遗留静态路由。见配置基线。这是本部分结束时的三路由器运行配置，不能直接当成下一部分四路由器的最终启动配置。

## 云侧 AS65003 接入

记录日期：2026-10-25｜实验：G0-IOL-Basic

### 拓扑与地址

增加 R4，使用 AS65003 模拟云侧边界，经 R3 接入现有网络。这里的“云侧”指实验角色，仍是普通 IOL 路由器，不涉及真实云平台、专线或云产品部署。


前面的 R1—R2、R2—R3 连线和配置保留；新增 R3 Ethernet0/1 到 R4 Ethernet0/0 的连线。R3 已经运行 BGP，现在只增加一个邻居；R4 则要配置自己的 AS、邻居和 Loopback 发布。

| 设备 | 接口 | 地址 | AS |
| --- | --- | --- | --- |
| R3 | Ethernet0/1 | 10.34.0.1/30 | 65002 |
| R4 | Ethernet0/0 | 10.34.0.2/30 | 65003 |
| R4 | Loopback0 | 10.255.0.4/32 | 65003 |

### 配置直连链路

在 EVE 添加同镜像 R4，保存并停止涉及连线的节点，连接 R3 Ethernet0/1 与 R4 Ethernet0/0，再启动。R4 首次启动时跳过初始配置向导。

R3 在 Ethernet0/1 配置 10.34.0.1/30 并启用接口：

```text
configure terminal
interface Ethernet0/1
 ip address 10.34.0.1 255.255.255.252
 no shutdown
end
show ip interface brief
```

![R3接口配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/e0c40a9ffe399eb89d11.png)

R4 从首次启动的用户模式开始，配置 Ethernet0/0 和 Loopback0：

```text
enable
configure terminal
hostname R4
interface Ethernet0/0
 ip address 10.34.0.2 255.255.255.252
 no shutdown
exit
interface Loopback0
 ip address 10.255.0.4 255.255.255.255
end
show ip interface brief
ping 10.34.0.1
copy running-config startup-config
```

接口与直连验证结果：R4 两个接口均为 up/up。

![R4接口与Loopback配置](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/b8af24ca2889339e3d3c.png)

R4 到 10.34.0.1 首次 ping 为 4/5，重测 5/5；保存返回 `[OK]`。

![R4直连测试及保存](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/d60cf3e1629e9586d159.png)

### 建立 eBGP

R3：

```text
configure terminal
router bgp 65002
 neighbor 10.34.0.2 remote-as 65003
end
```

![R3添加云侧邻居](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/b52bfff3fb5c5baa4174.png)

R4：

```text
configure terminal
router bgp 65003
 bgp router-id 4.4.4.4
 neighbor 10.34.0.1 remote-as 65002
 network 10.255.0.4 mask 255.255.255.255
end
```

![R4配置AS65003](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/434f253281b6cee48325.png)

R3 验证：

```text
show ip bgp summary
ping 10.255.0.4 source 10.255.0.3
```

R3 从 R2 收到两个前缀，从 R4 收到一个前缀，两个邻居均建立；到 R4 Loopback 的 ping 为 5/5。

![R3邻居与连通验证](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/1e4b9d5569938eee5330.png)

R4 验证：

```text
show ip bgp summary
show ip route bgp
ping 10.255.0.3 source 10.255.0.4
```

R4 从 R3 收到 `10.255.0.1/32`、`10.255.0.2/32`、`10.255.0.3/32`，下一跳均为 `10.34.0.1`；到 R3 Loopback 的 ping 为 5/5。

R3 可以将从 R2 学到的合适 BGP 路由继续通告给 R4，所以这里不需要在 R3 为每个总部 Loopback 再写一条 `network`。`network` 用于向 BGP 发起发布，本实验中转已有 BGP 路由依赖的是 BGP 的路由选择和通告机制。

![R4路由与连通验证](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/ced300b1d1e4789356f2.png)

### 放行云侧前缀进入总部 OSPF

R4 已有到总部的路由，但总部还需要返回云侧的路由。先在 R2 查询 `show ip route 10.255.0.4`，确认前缀已通过 BGP 到达，下一跳为 10.23.0.2，AS Hops 为 2。

R4 已学到总部地址，说明它知道如何把请求送往总部；但 R1 的 OSPF 仍只允许引入 `10.255.0.3/32`，它还没有回到 R4 Loopback 的路径。R2 收到云侧 BGP 路由，并不表示 R1 已经同步收到。

下面命令在 **R2** 的 `R2#` 下输入，在既有重分发白名单中增加精确匹配：

```text
configure terminal
ip prefix-list DC-LOOPBACK seq 20 permit 10.255.0.4/32
end
```

`DC-LOOPBACK` 沿用旧名称，现允许 DC 与 CLOUD 两个 Loopback。原 route-map 已引用该列表，无需重建。

![R2放行云侧前缀](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/66d0a19ebabff070036e.png)

### 总部与云侧互通

R1 学到 10.255.0.4/32 的 OSPF E1 路由，metric 30，下一跳为 10.12.0.2。

```text
! R1
show ip route 10.255.0.4
ping 10.255.0.4 source 10.255.0.1
! R4
ping 10.255.0.1 source 10.255.0.4
```

两个方向均为 5/5。

![R1云侧路由与ping](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/1ee90db0f6ec19407fae.png)

![R4返回总部ping](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/0a151896813e4487507e.png)

R1 的下一跳仍是相邻的 R2（`10.12.0.2`），不是远端 R4 的 `10.34.0.2`。每台路由器只需知道当前应交给哪个下一跳，报文依次经过 R2、R3，最后到 R4；回包也依赖沿途设备的反向路由。

四路由器运行状态下的路由互通已验证。新增 BGP 和白名单配置的保存输出未单独留存；R4 直连配置保存有截图记录。保存与回读的复现操作为：四台分别执行 `copy running-config startup-config`，再核对启动配置；该项完整输出待补。

## 路由标记与状态对照

| 标记或状态 | 含义 | 验证范围 |
| --- | --- | --- |
| 接口 up/up | 本机接口和链路协议处于工作状态 | 远端 Loopback 一定可达 |
| `C` | 网段直接连接在本机接口上 | 其他设备知道这个网段 |
| `S` | 使用手工配置的静态路由 | 动态路由协议正在工作 |
| OSPF `FULL` | 这对邻居完成了数据库同步 | 指定目标已正确发布或业务已通 |
| `O` | OSPF 区域内路由 | 路由来自外部 BGP |
| `O E1` | 进入 OSPF 的外部类型 1 路由 | 该目标原本属于总部内部 OSPF |
| BGP `State/PfxRcd` 为数字 | 会话已建立，并显示收到的前缀数 | 所有业务需要的前缀都已收到 |
| `B` | 路由表选用了 BGP 来源的路由 | 下游 OSPF 也自动收到了它 |
| 指定 Loopback 源 ping 5/5 | 本次这对源、目的地址具备可用的请求及应答路径 | 重启后一定保留配置，或其他地址也一定可通 |

配置保存、路由学习和通信测试分别回答不同问题。回看时可以沿着一条具体路径检查：目标属于谁，本机有没有到它的路由，下一跳是否可达，对方有没有回到源地址的路由。

![EVE Windows Client Pack 3.0 安装向导](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/3c1587a5567f23b6bc4a.png)

#### 安装位置与组件

保留客户端默认目录 `C:\Program Files\EVE-NG`。安装器明确提示：选择安装 Wireshark 和 UltraVNC 时，不要修改它们各自的安装目录。相关启动脚本和协议关联可能依赖默认路径，安装后也不要直接移动程序文件夹。

![安装器说明默认路径，并要求保留 Wireshark 与 UltraVNC 的安装目录](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/125b2041070c414750bf.png)

![客户端组件选择：PuTTY、协议关联、Wireshark 与 UltraVNC](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/ccie-lab/149a9d4d0b8de0e47688.png)

#### 使用 Native 控制台

1. 安装完成后，退出 EVE 网页登录。
2. 登录页面选择 `Native console`，重新登录。
3. 启动实验节点，再双击打开控制台。

| 现象 | 检查方向 |
