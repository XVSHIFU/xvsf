#### 创建实例账户（参考内容）

````shell
## 1. 创建 ServiceAccount

创建 `dashboard-adminuser.yaml`，写入：

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: admin-user
  namespace: kubernetes-dashboard
```

执行：

```bash
kubectl apply -f dashboard-adminuser.yaml
```

即可在 `kubernetes-dashboard` 命名空间中创建一个名为 `admin-user` 的 ServiceAccount。

## 2. 创建 ClusterRoleBinding（集群角色绑定）

ServiceAccount 仅代表身份，默认不具备集群管理员权限。

ClusterRoleBinding 用于将 ClusterRole（集群角色）绑定到 ServiceAccount，使其获得相应权限。

在 `dashboard-adminuser.yaml` 中追加以下内容（使用 `---` 分隔资源）：

```yaml
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: admin-user
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: ServiceAccount
    name: admin-user
    namespace: kubernetes-dashboard
```

执行：

```bash
kubectl apply -f dashboard-adminuser.yaml
```

即可将 `cluster-admin` 集群管理员权限授予 `admin-user`。

查看绑定：

```bash
kubectl get clusterrolebinding admin-user
```

权限关系：

- ServiceAccount：身份（谁）
- ClusterRole：权限（能做什么）
- ClusterRoleBinding：授权关系（将权限授予谁）
- RoleBinding：仅在指定命名空间内授予权限
- ClusterRoleBinding：在整个集群范围内授予权限

## 3. 获取登录 Dashboard 的令牌

获取短期 Token：

```bash
kubectl -n kubernetes-dashboard create token admin-user
```

指定 Token 有效时间（例如 24 小时）：

```bash
kubectl -n kubernetes-dashboard create token admin-user --duration=24h
```

注意：实际有效期可能受到 API Server 配置限制。

### 长期 Token

创建 `dashboard-adminuser-secret.yaml`，写入：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: admin-user
  namespace: kubernetes-dashboard
  annotations:
    kubernetes.io/service-account.name: "admin-user"
type: kubernetes.io/service-account-token
```

执行：

```bash
kubectl apply -f dashboard-adminuser-secret.yaml
```

获取长期 Token：

```bash
kubectl get secret admin-user -n kubernetes-dashboard -o jsonpath="{.data.token}" | base64 -d
```

注意：长期 Token 不会自动过期，存在较高的泄露风险，建议优先使用短期 Token。

## 4. 登录 Dashboard

复制获取的 Token，在 Dashboard 登录页面选择 Token 登录，粘贴后点击 `Sign in`。

注意：Token 登录需要通过 HTTPS 访问 Dashboard。

## 5. 验证权限

检查 `admin-user` 是否具有删除 Pod 的权限：

```bash
kubectl auth can-i delete pods \
  --as=system:serviceaccount:kubernetes-dashboard:admin-user \
  --all-namespaces
```

返回 `yes` 表示权限检查通过。

## 6. 删除资源

删除管理员 ServiceAccount：

```bash
kubectl -n kubernetes-dashboard delete serviceaccount admin-user
```

删除 ClusterRoleBinding：

```bash
kubectl delete clusterrolebinding admin-user
```

删除长期 Token 对应的 Secret（如果创建过）：

```bash
kubectl -n kubernetes-dashboard delete secret admin-user
```

注意：ClusterRoleBinding 是集群级资源，不属于任何命名空间，因此删除时不需要指定 `-n`。

以上操作仅删除创建的账户、绑定和 Secret，不会删除 Kubernetes Dashboard 本身。
````

```yaml
            apiVersion: client.authentication.k8s.io/v1

            interactiveMode: Never
            provideClusterInfo: true
    plugins:
      - name: secretreader
        image: registry.k8s.io/cluster-inventory-api/secretreader:v0.1.3@sha256:ec3090dc166aa2b42fb35d714d161c417d8b27bbc463404c8f615f5f4c610a1d
```

#### 扩缩容与自动恢复

Kubernetes 根据集群中 Deployment 对象的期望状态管理 Pod。

修改本地 YAML 后需要执行 `kubectl apply` 才会生效；

通过 Headlamp 或 `kubectl scale` 修改，则直接更新集群中的对象。

Kubernetes 不会持续读取本地 YAML 文件。

```yaml
spec:
  replicas: 2
```

![image-20261013114249435](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/image-20261013114249435.png)

> k8s 会不断让实际运行的 Pod 数量，接近 deployment 中设定的期望数量
>
> 扩缩容：spec.replicas 配置期望数量
>
> 自动恢复：控制器会按照期望数量进行创建、删除 Pod

```yaml
          volumeMounts:

              mountPath: /usr/share/nginx/html
```

## 3．存储  Volume、PV、PVC


| 概念                             | 作用                              | 可以这样理解         |
| -------------------------------- | --------------------------------- | -------------------- |
| **Volume**                       | 在 Pod 中声明存储，供容器挂载使用 | 容器使用数据的入口   |
| **PV**（PersistentVolume）       | 集群中的持久存储资源              | 实际可提供的存储空间 |
| **PVC**（PersistentVolumeClaim） | 应用对存储容量、访问方式的申请    | 应用提交的存储申请单 |

使用持久存储时：**PVC 绑定 PV，Pod 通过 Volume 引用 PVC，容器通过 `volumeMounts` 挂载到目录**

几种数据的生命周期：


| 数据位置         | 容器重建后                | Pod 删除并重建后               |
| ---------------- | ------------------------- | ------------------------------ |
| 容器自身的可写层 | 数据不保留                | 数据不保留                     |
| `emptyDir` 卷    | 同一个 Pod 内仍保留       | 数据删除                       |
| `ConfigMap` 卷   | 从 ConfigMap 重新提供内容 | ConfigMap 仍在即可重新挂载     |
| PVC 对应的持久卷 | 数据通常保留              | PVC 和底层存储仍在即可重新挂载 |

**ConfigMap 用于提供配置，不适合存放数据库、上传文件等需要应用写入的数据。**


### StorageClass + 动态供应

**StorageClass + 动态供应**：创建 PVC 后，由供应器自动创建 NFS 子目录和 PV。

使用 Kubernetes SIGs 的 [NFS Subdir External Provisioner](https://github.com/kubernetes-sigs/nfs-subdir-external-provisioner)，可以利用已经搭好的 NFS 服务器完成动态供应。[GitHub](https://github.com/kubernetes-sigs/nfs-subdir-external-provisioner)

**1. 在 master 上添加 Helm 仓库**

```bash
helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/

helm repo update
```

**2. 创建供应器配置文件**

在 master 上执行：

```bash
cat > nfs-values.yaml <<'EOF'
nfs:
  server: 192.168.194.141
  path: /data/nfs/nginx-demo
  mountOptions:
    - nfsvers=4

storageClass:
  create: true
  name: nfs-client
  defaultClass: false
  reclaimPolicy: Retain
  allowVolumeExpansion: false

nodeSelector:
  kubernetes.io/hostname: node1
EOF
```

这些是 **Helm Chart 的配置项**，由 Helm 转换为 Kubernetes 资源：


| 配置                          | 本次的作用                              |
| ----------------------------- | --------------------------------------- |
| `nfs.server`、`nfs.path`      | 使用已有的 NFS 共享目录                 |
| `storageClass.create: true`   | 安装时自动创建 StorageClass             |
| `name: nfs-client`            | 后续 PVC 用这个名字选择存储             |
| `defaultClass: false`         | PVC 需要明确填写 StorageClass 名称      |
| `reclaimPolicy: Retain`       | 创建出的 PV 使用保留策略                |
| `allowVolumeExpansion: false` | 关闭该供应器不支持的卷扩容              |
| `nodeSelector`                | 将供应器安排到已验证能访问 NFS 的 node1 |

**3. 安装供应器**

继续在 master 上执行：

```bash
helm install nfs-provisioner \
  nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
  --namespace nfs-provisioner \
  --create-namespace \
  -f nfs-values.yaml
```

### StatefulSet

之前的 Deployment ，Pod 重建后名称会变化，而 StatefulSet 为每个副本保留稳定的身份，并能通过 PVC 模板给每个副本分配独立存储

2、创建 StatefulSet 和无头 Service

```shell
vim statefulset-demo.yaml
```

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-headless
  namespace: workload-demo
spec:
  clusterIP: None
  selector:
    app: stateful-web
  ports:
    - name: http
      port: 80
      targetPort: 80
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
  namespace: workload-demo
spec:
  serviceName: web-headless
  replicas: 2
  selector:
    matchLabels:
      app: stateful-web
  template:
    metadata:
      labels:
        app: stateful-web
    spec:
      containers:
        - name: nginx
          image: nginx:stable
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 128Mi
          volumeMounts:
            - name: html
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: html
      spec:
        accessModes:
          - ReadWriteMany
        storageClassName: nfs-client
        resources:
          requests:
            storage: 1Gi
```


| 配置                        | 作用                                           |
| --------------------------- | ---------------------------------------------- |
| `clusterIP: None`           | 创建无头 Service，不分配普通的 Service 虚拟 IP |
| `serviceName: web-headless` | 关联 Service，支持 Pod 的稳定 DNS 名称         |
| `replicas: 2`               | 创建 `web-0`、`web-1`                          |
| `volumeClaimTemplates`      | 为每个 Pod 自动创建独立 PVC                    |
| `volumeMounts.name: html`   | 将该 Pod 对应的 `html` 存储挂载到容器          |

虽然这里使用 NFS 的 ReadWriteMany ，但俩个 Pod 仍然各自使用一个 PVC，并不会因此共享一个目录

- `persistentVolumeReclaimPolicy` 是 `Retain`。
- `storageClassName` 是 `nfs-client`。
- `claimRef` 指向旧的 `nginx-auto-data`。

`Released` 表示旧 PVC 已释放该卷，但 PV 仍记录旧绑定关系，尚不能直接给新 PVC 使用

#### **一、找回之前 Retain 保留的数据**

**1. 创建一个指定旧 PV 的新 PVC**

```shell
cat > recover-pvc.yaml <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nginx-recovered-data
  namespace: nginx-demo
spec:
  storageClassName: nfs-client
  volumeName: ${RETAIN_PV}
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 1Gi
EOF

kubectl apply -f recover-pvc.yaml
```

这里的关键是：

```text
volumeName: 旧PV名称
```

它要求绑定这个旧 PV，不会另外动态创建一个新卷。此时 PVC 暂时 `Pending` 是正常的

**2. 清除旧绑定记录**

仅对刚确认的 **Released 实验 PV** 执行：

```bash
kubectl patch pv "$RETAIN_PV" --type=merge \
  -p '{"spec":{"claimRef":null}}'
```

这一步只清除旧 PVC 的绑定记录，**不会清空 NFS 文件**。

查看结果：

```bash
kubectl get pvc nginx-recovered-data -n nginx-demo
kubectl get pv "$RETAIN_PV"
```

![image-20261013204740035](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/image-20261013204740035.png)

两者都变成 `Bound`，PV 的 CLAIM 变为：

#### **二、验证 Delete 回收策略**

这次新建专门的测试卷，用完后会删除它的数据。

对于的 `nfs-subdir-external-provisioner`，**PV 被删除不一定意味着文件也被删除**：供应器可以把目录归档。本实验显式设置 `onDelete: "delete"`，让它真正删除测试目录

**1. 创建专用 StorageClass**

先读取现有供应器的名称：

```shell
NFS_PROVISIONER=$(kubectl get storageclass nfs-client \
  -o jsonpath='{.provisioner}')

echo "$NFS_PROVISIONER"
```

然后创建：

```shell
cat > nfs-delete-class.yaml <<EOF
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-delete-demo
provisioner: ${NFS_PROVISIONER}
parameters:
  onDelete: "delete"
reclaimPolicy: Delete
volumeBindingMode: Immediate
mountOptions:
  - nfsvers=4
EOF

kubectl apply -f nfs-delete-class.yaml
```

两个设置分别控制：


| 配置                    | 作用                                      |
| ----------------------- | ----------------------------------------- |
| `reclaimPolicy: Delete` | PVC 释放后，触发卷回收并删除 PV           |
| `onDelete: "delete"`    | 告诉这个 NFS 供应器删除对应目录，而非归档 |

**2. 创建测试 PVC 和 Pod**

```bash
vim delete-demo.yaml
```

写入：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: delete-demo-data
  namespace: nginx-demo
spec:
  storageClassName: nfs-delete-demo
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: delete-demo
  namespace: nginx-demo
spec:
  containers:
    - name: nginx
      image: nginx:stable
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: delete-demo-data
```

应用并写入测试文件：

```bash

kubectl wait --for=condition=Ready pod/delete-demo \
  -n nginx-demo --timeout=120s

  sh -c 'echo "This data is disposable" > /usr/share/nginx/html/delete-test.txt'
```

## 4．网站入口

### Ingress

- Traefik 实际接收、转发请求
- Ingress 定义域名、路径、Service的对应规则
- Service 根据标签关联后端 Pod
- 路由到`/app2/`时，后端也必须能处理该路径；Ingress 不会自动去掉`/app2`

### Ingress 与域名访问

- **Ingress**：声明“哪个域名、哪个路径交给哪个 Service”。
- **Ingress Controller**：实际接收请求并执行这些规则的程序。

只创建 Ingress 对象不会自动产生入口，必须安装控制器。本次使用 **Traefik**。Ingress API 仍可使用，不过 Kubernetes 官方已冻结其新功能，后续还可以学习 Gateway API

**第三步：通过 Headlamp 创建 Ingress**

在 Headlamp「新增」中提交：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress
  namespace: nginx-demo
spec:
  ingressClassName: traefik
  rules:
    - host: nginx.demo.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx
                port:
                  number: 80
```


| 配置                          | 作用                                          |
| ----------------------------- | --------------------------------------------- |
| `namespace: nginx-demo`       | 与后端 nginx Service 位于同一命名空间         |
| `ingressClassName: traefik`   | 由 Traefik 控制器处理                         |
| `host: nginx.demo.test`       | 匹配请求中的域名                              |
| `path: /`、`pathType: Prefix` | 匹配 `/` 及其下面的路径                       |
| `service.name: nginx`         | 使用 nginx Service 作为后端                   |
| `port.number: 80`             | 填 Service 的 `port`，**不是 NodePort 30081** |

### **Secret + HTTPS**

给俩个应用启用 HTTPS ，同时学习如何保存证书和私钥


| 对象            | 作用                                         |
| --------------- | -------------------------------------------- |
| 证书 `demo.crt` | 包含域名、公钥等信息，供客户端验证服务端身份 |
| 私钥 `demo.key` | 服务端使用的秘密文件，需要妥善保管           |
| TLS Secret      | 在 Kubernetes 中保存证书和私钥               |
| Ingress         | 指定域名使用哪个 Secret                      |
| Traefik         | 读取证书，处理 HTTPS 请求并转发到应用        |

HTTPS 加密发生在浏览器与 Traefik 之间，Traefik 到后端 nginx 仍使用 HTTP 80

#### 确认 HTTPS 入口

master

```shell

```

#### 生成实验用自签名证书

```shell
mkdir -p ~/k8s-tls-demo
cd ~/k8s-tls-demo

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout demo.key \
  -out demo.crt \
  -subj "/CN=nginx.demo.test" \
  -addext "subjectAltName=DNS:nginx.demo.test,DNS:app2.demo.test"

chmod 600 demo.key
```


| 参数               | 含义                             |
| ------------------ | -------------------------------- |
| `-x509`            | 生成自签名证书                   |
| `-nodes`           | 私钥不设置口令，便于服务自动读取 |
| `-days 365`        | 有效期 365 天                    |
| `-newkey rsa:2048` | 同时生成 RSA 私钥                |
| `-keyout` / `-out` | 私钥与证书的输出文件             |
| `subjectAltName`   | 证书覆盖的域名，这里包含两个     |

#### 将证书保存为 Secret

```shell
kubectl create secret tls demo-tls \
  --cert=demo.crt \
  --key=demo.key \
  -n nginx-demo
```


```yaml
  ingressClassName: traefik
  tls:
    - hosts:
        - nginx.demo.test
        - app2.demo.test

  rules:
    - host: nginx.demo.test

        paths:
          - path: /app2
            pathType: Prefix
            backend:
              service:
                name: app2
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx
                port:
                  number: 80
    - host: app2.demo.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app2

                  number: 80
```

### 健康检查与资源限制


| 探针                      | 检查什么         | 连续失败后的处理                    |
| ------------------------- | ---------------- | ----------------------------------- |
| `readinessProbe` 就绪探针 | 能否接收请求     | Service 停止向这个 Pod 分配正常流量 |
| `livenessProbe` 存活探针  | 应用是否仍然健康 | 重启这个容器                        |


| 探针                          | 作用                     | 连续失败达到阈值后                                         | 成功后                                 |
| ----------------------------- | ------------------------ | ---------------------------------------------------------- | -------------------------------------- |
| `startupProbe` **启动探针**   | 判断应用是否完成启动     | 在当前 Deployment 中重启容器                               | 停止启动检查，允许另外两种探针开始工作 |
| `readinessProbe` **就绪探针** | 判断应用能否接收请求     | Pod 标记为未就绪，Service 不再向它分配正常流量；**不重启** | Pod 恢复就绪后重新接收流量             |
| `livenessProbe` **存活探针**  | 判断应用是否需要重启恢复 | 在当前 Deployment 中重启容器                               | 继续定期检查                           |

### **资源 requests / limits**


| 配置       | CPU                           | 内存                                     |
| ---------- | ----------------------------- | ---------------------------------------- |
| `requests` | 调度时需要预留的 CPU 配额依据 | 调度时需要预留的内存容量依据             |
| `limits`   | 使用上限，达到上限会被限速    | 使用上限，超过时可能触发 OOM，容器被终止 |

requests 不是实际消耗，也不是使用上限

即使申请了 64Mi,nginx 也可以只使用 5Mi，有可用资源时，也可以使用超过 requests 的资源，但受 limits 约束，

配置：

```yaml
resources:
  requests:
    cpu: 100m
    memory: 64Mi
   limits:
     cpu: 500m
     memory: 128Mi
```

### **HPA 自动扩缩容**

让 Kubernetes 根据资源用量自动调整副本数量

我们设置 CPU 目标利用率为 50%，这个百分比以 requests.cpu 为基准，不是 limits，每个 nginx 容器申请了 100m，因此`目标 CPU 用量 = 100m × 50% = 50m`

#### 创建 HPA

master 创建文件：

```shell
vim nginx-hpa.yaml
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
  namespace: nginx-demo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  minReplicas: 2
  maxReplicas: 4
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
```


| 配置                     | 含义                                  |
| ------------------------ | ------------------------------------- |
| `scaleTargetRef`         | 管理同命名空间中的 Deployment `nginx` |
| `minReplicas: 2`         | 至少保留两个副本                      |
| `maxReplicas: 4`         | 最多扩到四个副本                      |
| `averageUtilization: 50` | CPU 平均目标利用率为 requests 的 50%  |

应用：

```shell
kubectl apply -f nginx-hpa.yaml
kubectl get hpa -n nginx-demo
```

`1%/50%` 表示 **当前利用率 / 目标利用率**

```shell
nginx-hpa   Deployment/nginx   cpu: 15%/50%    2         4         4          11m
nginx-hpa   Deployment/nginx   cpu: 1%/50%     2         4         4          12m



```

![image-20261013181925133](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/image-20261013181925133.png)

从实验中可以看到，副本数从 2 增加到了 4，负载降低后，进行了缩容


| 输出                      | 含义                                     |
| ------------------------- | ---------------------------------------- |
| `1%/50%`，2 个副本        | CPU 用量低，保持最少 2 个副本            |
| `106%/50%`，2 → 4 个副本 | 超过目标值，HPA 自动扩容                 |
| `125%/50%`，4 个副本      | 仍超过目标，但已达到上限 4，不能继续增加 |
| `1%/50%`，仍为 4 个副本   | 负载停止，等待缩容稳定窗口               |

这里以 `requests.cpu: 100m` 为基准。假设忙循环所在的 Pod 使用约 `500m`，另外三个几乎空闲：

$$
\text{平均每个 Pod 用量} \approx \frac{500m}{4} = 125m
$$

$$
\text{平均利用率} \approx \frac{125m}{100m} \times 100\% = 125\%
$$

125% 不代表突破了 limits ，只是超过了 requests

忙循环只在原来的一个 Pod 内运行，新增 Pod 不会接手这个循环，因此扩容后那个 Pod 仍然繁忙

继续等待了一会，回到了 2 个副本，这样就完成了 **低负载-加压-自动扩容-停止加压-自动缩容** 的完整过程

![image-20261013182814782](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/image-20261013182814782.png)

#### 水平扩容和垂直扩容

- 垂直扩容就是增加单个 Pod 的 CPU、内存资源
- 水平扩容则是增加 Pod 的数量

比如 nginx，水平扩容（HPA），调整前是 2 个 Pod ，调整后，变成 4 个 Pod ，每个的资源配置不变；如果是垂直扩容，调整前每个 Pod 申请 `100m CPU  64Mi Memory`，调整后，每个 Pod 申请 `200m CPU   128Mi Memory`.

手动修改 Deployment 中的 resources.requests / limits 就是在调整单个容器的资源配置

**VPA（Vertical Pod Autoscaler）是把资源调整自动化的组件**：分析历史资源使用情况，给出合适的 requests 建议，也可以按配置自动应用。它主要调整 requests，limits 是否跟随调整取决于策略

- **安装 Metrics Server 不会自动安装 VPA**，VPA 需要单独部署
- 资源调整是否需要重建 Pod，取决于 Kubernetes 版本、VPA 版本和更新模式，不能理解为一定无中断

总：**HPA 加 Pod 数量、VPA 调单个 Pod 的资源大小**

#### 节点亲和性  nodeAffinity

它比 `nodeSelector` 更灵活：


| 类型   | 配置名称                                          | 含义                                       |

##### **1．修改调度配置**

```bash
vim scheduling-demo.yaml
```

删除原来的：

```text
      nodeSelector:
        scheduling-demo: green
```

在相同位置改成下面的 `affinity`。注意它与 `containers` 同级：

```yaml
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: scheduling-demo
                    operator: In
                    values:
                      - blue
                      - green
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: scheduling-demo
                    operator: In
                    values:
                      - green
      containers:
        # 原来的容器配置保持不变
```

含义：

- **required**：节点的 `scheduling-demo` 必须是 `blue` 或 `green`，对应 node1、node2。
- **preferred**：在符合条件的节点中，优先选择 `green`，对应 node2。
- **weight: 100**：这条偏好的权重，不代表百分之百保证选中。

**必须删除原来的 `nodeSelector`**，否则它仍会要求节点必须是 `green`，无法实现向 node1 回退。

应用：

```bash
kubectl rollout status deployment/scheduling-demo \
  -n workload-demo --timeout=120s

kubectl get pods -n workload-demo \
  -l app=scheduling-demo -o wide
```

#### 污点与容忍（Taints / Tolerations）

- 污点设置在节点上：拒绝不符合条件的 Pod
- 容忍设置在 Pod 上：允许 Pod 通过对应污点的限制
- 容忍不等于指定节点：通过限制后，还要满足节点选择、资源等其他条件

##### **1．给 node2 添加污点**

在 master 执行：

```bash
kubectl taint nodes node2 training=reserved:NoSchedule
```


| 部分         | 含义                                |
| ------------ | ----------------------------------- |
| `training`   | 污点的键                            |
| `reserved`   | 污点的值                            |
| `NoSchedule` | 不允许没有对应容忍的新 Pod 调度进来 |

查看：

```bash
kubectl get node node2 -o jsonpath='{.spec.taints}{"\n"}'
```

**这个污点不会驱逐 node2 上已经运行的 Pod**，但会影响后续新 Pod 的调度。实验完成后会删除它。

![image-20261014132357201](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/image-20261014132357201.png)

##### **3．给 Pod 添加容忍**

编辑：

```bash
vim taint-demo.yaml
```

在 `nodeSelector` 后面添加 `tolerations`，与 `containers` 同级：

```yaml
    spec:
      nodeSelector:
        scheduling-demo: green
      tolerations:
        - key: training
          operator: Equal
          value: reserved
          effect: NoSchedule
      containers:
        - name: nginx
          image: nginx:stable
          resources:
            requests:
              cpu: 50m
              memory: 32Mi
            limits:
              cpu: 200m
              memory: 64Mi
```

容忍规则与污点对应：

```text
training=reserved:NoSchedule
```

`operator: Equal` 表示键和值都要匹配，`effect` 也要对应。

应用并查看：

```bash
kubectl apply -f taint-demo.yaml

kubectl rollout status deployment/taint-demo \
  -n workload-demo --timeout=120s

kubectl get pods -n workload-demo -l app=taint-demo -o wide
```

![image-20261014132610007](https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/image-20261014132610007.png)

这里两个配置共同起作用：


| 配置           | 作用                            |
| -------------- | ------------------------------- |
| `nodeSelector` | 要求选择 node2                  |
| `tolerations`  | 允许通过 node2 上的这条污点限制 |

##### **5．认识三种污点效果**


| 效果               | 对没有匹配容忍的 Pod 的影响                 |
| ------------------ | ------------------------------------------- |
| `NoSchedule`       | 禁止新 Pod 调度进来，已有 Pod 不受影响      |
| `PreferNoSchedule` | 尽量不调度进来，是软限制                    |
| `NoExecute`        | 禁止新 Pod 调度进来，并驱逐已有的不容忍 Pod |

#### **drain 节点维护**

drain 用于节点维护前，驱逐节点上的应用 Pod，并停止该节点接收普通新 Pod，Deployment、StatefulSet 等控制器再创建替代 Pod，由调度器安排到符合条件的节点

##### **1．确认实验污点已删除**

```bash
kubectl get node node2 -o jsonpath='{.spec.taints}{"\n"}'
```

如果仍有 `training=reserved:NoSchedule`，执行：

```bash
kubectl taint nodes node2 training=reserved:NoSchedule-
```

##### **2．查看 node2 上实际运行的 Pod**

```bash
kubectl get pods -A --field-selector spec.nodeName=node2 -o wide
```

再查看这些 Pod 由谁管理：

```bash

  -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,OWNER-KIND:.metadata.ownerReferences[0].kind,OWNER-NAME:.metadata.ownerReferences[0].name'
```

主要看 `OWNER-KIND`：


| 显示          | 含义                                     |
| ------------- | ---------------------------------------- |
| `ReplicaSet`  | 通常由 Deployment 间接管理，可以自动补建 |
| `StatefulSet` | 可以重建同名 Pod，并关联原 PVC           |
| `DaemonSet`   | drain 通常需要跳过，相关 Pod 留在节点上  |
| `<none>`      | 没有控制器，删除后不会自动补建           |

**有控制器也不意味着一定能迁移成功**：新节点还必须满足资源、存储、节点选择等条件。

##### **3．预览 drain，不实际驱逐**

```bash
kubectl drain node2 --ignore-daemonsets --dry-run=server
```

参数含义：

- `--ignore-daemonsets`：允许跳过 DaemonSet Pod，例如 Flannel、kube-proxy、node-reporter；不会删除它们。
- `--dry-run=server`：预演请求，不真正执行节点腾空。它不能保证实际迁移一定成功。
